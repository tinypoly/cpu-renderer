# Architecture

This document describes how `@tinypoly/cpu-renderer` works inside. For installation and usage, see the [README](README.md).

The renderer runs this software rasterizer in a pool of workers: Web Workers in the browser, `worker_threads` in Node (one per core minus one, capped at eight automatically; manual selection allows up to `MAX_RENDER_WORKERS` with shared memory). Geometry processing, shader interpretation, visibility, lighting, sampling, depth of field and color conversion execute on the CPU. Completed buckets are handed to the host through the `pixels` event and kept in `image`; `attachCanvas` paints them on a Canvas 2D, and saving the image is plain canvas-to-PNG (or a PNG encoder over `image.data` in Node) on the host's side. `CpuRenderer` itself touches no DOM API. No WebGL renderer, GPU path tracer, or WebGPU device is created by this engine.

The host application builds its scene with Three.js and keeps its own camera controls. Three remains a dependency for scene data, math and HDR decoding.

## Modules

- `rasterizer.ts`: clipping, projection, bucket binning, coverage, perspective interpolation, depth, per-pixel transparency, antialiasing and thin-lens sampling. Without depth of field a bucket is one pass: coverage and depth are evaluated per sample, but each pixel is shaded once per triangle (MSAA style, at the first covered sample). Depth of field falls back to one pass per lens sample. A pass first records which triangles cover each pixel, then shades pixel by pixel in row order, replaying that pixel's triangles in draw order (so depth, blending and the image match a triangle-first loop) and resolving the pixel before moving on.
- `material.ts`: built-in material evaluators and custom shader stages.
- `compute.ts`: fragment-pass execution over float buffers, iterations, ping-pong state, uniform bindings and restored snapshots.
- `pipeline.ts`: cached simulation bakes and CPU planar reflection, environment and refraction/depth captures.
- `glsl.ts`: tokenizer, parser, preprocessor and a closure compiler: the syntax tree is turned once into nested JavaScript closures with fixed variable slots, and each fragment only runs those closures. Loops and calls are bounded by an instruction budget. Shader source never passes through `eval` or `Function`.
- `texture.ts`: texture addressing, transforms, filtering and sRGB decoding.
- `environment.ts`: HDR/gradient backgrounds, procedural sky shader baking, per-pixel celestial bodies and environment convolution.
- `globalIllumination.ts`: diffuse path integration, cosine sampling, emissive triangle sampling with MIS, and indirect sample clamping.
- `bvh.ts`: immutable acceleration structure for closest GI hits and direct-light shadow queries, stored in flat typed arrays and traversed iteratively with scalar math; triangles without alpha maps accept the hit without interpolating attributes.
- `preparedGeometry.ts`: the flat, shareable layout of a prepared frame. Vertices after the vertex shader (clip, world, normal, point size, attributes and flattened varyings per group layout), triangles as group + vertex offsets, per-triangle flags, world positions and face normals, bucket bins and the BVH. Flat-shaded triangles keep their original vertices and read the face normal.
- `sharedBuffers.ts`: typed array allocation in `SharedArrayBuffer` when the page is cross-origin isolated, or in Node.
- `color.ts`: CPU ACES, AgX, neutral and linear display transforms.
- `sceneSerialization.ts` and `sceneSignature.ts`: scene snapshots (shared memory when cross-origin isolated) and change detection.
- `settings.ts`: the public `RenderSettings` (grouped by feature), the environment and the camera state, and `toFrameSettings`.
- `frameSettings.ts`: `FrameSettings`, the flat form of the settings the engine reads for one frame.
- `protocol.ts`: the messages between the renderer and the workers. Internal.
- `extensions.ts`: the options read from `userData.cpuRenderer` on scenes, objects, lights and materials.
- `renderer.ts`: `CpuRenderer`, the public class: inputs, `render()`, events, the worker pool and the `image` buffer. It talks to workers through `RenderWorker`, the `postMessage` / `onmessage` shape of a Web Worker.
- `canvas.ts`: `attachCanvas`, the Canvas 2D output: sizes the canvas at `start` and paints each `pixels` event.
- `bucketScheduler.ts`: the demand-driven bucket queue, one bucket in flight per worker.
- `events.ts`: the typed event emitter `CpuRenderer` extends.
- `workerHost.ts`: per-worker preparation, cancellation, pause/resume, environment loading and bucket rendering, independent of the transport.
- `worker.ts` and `workerNode.ts`: the worker entries, binding `workerHost.ts` to a Web Worker's global scope and to a `worker_threads` port.
- `node.ts`: published as `/node`; `createNodeWorker` starts `workerNode.js` in a thread and `wrapNodeWorker` gives it the `RenderWorker` shape.
- `shaderTypes.ts`: compute pipelines described as data, which a material runs through `userData.cpuRenderer.compute`.
- `index.ts` and `engine.ts`: the two entry points. `index.ts` is the public API around `CpuRenderer`; `engine.ts`, published as `/engine`, exposes the classes above for custom workers and scripts.

## Rendering lifecycle

1. `setScene` serializes the scene (`serializeScene`), which copies geometry and texture data. Transfer lists never contain the live scene's buffers. The other setters only record their input.
2. `render()` waits for the serialization, then posts one `frame` message with every input: the scene and the environment travel only when they changed. Each frame advances a revision, and the renderer ignores output from older revisions. A frame still in flight rejects with an `AbortError`.
3. The frame goes only to the first worker. It coalesces changes, loads and convolves the environment (or bakes the procedural sky), prepares material compute outputs and planar captures, runs the vertex stage and builds the triangles, bins and BVH, yielding between work units so incoming messages can cancel work. When the pool has readers it posts `prepared`; in every mode it reports `start`. The other workers receive `reset` when the revision opens and `adopt` with the prepared frame: they compile materials, rebuild the per-mesh uniforms and read the shared arrays, without repeating any of that work. Owner and readers render through the same accessors, so the image does not depend on which worker drew a bucket.
4. Buckets are ordered from the center outward. The client hands one bucket at a time to each ready worker and gives it the next when it reports back, so slow buckets (glass, heavy custom shaders) do not stall the others. While a bucket renders, the worker posts the rows resolved so far at most every 30 ms (`pixels` message) and the client copies just those rows into `image` and hands them out as a `pixels` event, so the image fills pixel by pixel; with depth of field each lens pass refines them. The completed bucket, with all requested samples, is still published at the end. The default is 64 × 64 pixels and four samples.
5. After the last bucket (and the denoiser, when the frame has one) `render()` resolves and `complete` fires. Pause stops every worker's pump; a new frame opens a new revision and drops stale buckets. `dispose()` terminates the pool.

Storage for samples and transparent fragments is local to a bucket, and so is a small cache of vertices decoded for projection. Scene attributes, textures, compute outputs, planar captures, environment levels and the prepared geometry (vertices, triangles, bins, BVH) are allocated in `SharedArrayBuffer` when the page is cross-origin isolated, so extra workers add only their compiled materials and bucket buffers. Outside isolation the renderer uses one worker, even if a larger pool was requested. That worker keeps its prepared frame, GI cache and denoise buffers locally instead of cloning them back to the page. Vertex data is stored as `Float64Array` so the shared path reproduces the previous floating point results exactly. Render targets are limited to 32 megapixels.

### GLSL scope

The interpreter supports scalar/vector arithmetic, square matrices, constructors, swizzles, one-dimensional arrays (including constructors, initialized/inferred lengths, `.length()` and function parameters), named global structs with nested fields, local scopes, function calls, `inout`/`out`, `if`, `for`, `while`, `do/while`, `switch` with fallthrough, `break`, `continue` and ternaries. Matrix operations include column/component reads and writes, component arithmetic, `transpose`, `determinant`, `inverse`, `matrixCompMult` and square `outerProduct`. Numeric inputs can include arrays of matrices and structs containing matrices. Indexed assignment and function copy-out capture indices once, including indices with side effects.

The preprocessor accepts object and function macros, nested/multiline arguments, conditional directives, include guards and compatible Three shader includes. Includes share `#define`/`#undef` state with the caller; comments and inactive branches do not execute directives. Expansion, include depth, shader calls and loops are bounded. The actual Three `common` chunk is covered by a test exercising its macros, light structs and scalar/vector overloads. Functions of equal arity use statically inferred argument types; ambiguous overloads produce a diagnostic. Integer expressions include truncating division, hexadecimal constants, bitwise compound assignments and unsigned shifts. This remains a subset of the [GLSL ES language](https://registry.khronos.org/OpenGL/specs/es/3.0/GLSL_ES_Specification_3.00.pdf), not a conformant GLSL compiler.

### Remaining limitations

- A simulation is a still snapshot. Its outputs are reused while the compute-pass inputs (`computeConfigKey`) stay the same, and a snapshot is restored exactly. Otherwise the declared passes bake in the interpreter at the material's `time`, with one 1/60 s step, so state a GPU simulation accumulates over many frames (wakes, foam, floating bodies) is only present when it comes in a snapshot.
- Compute resolution follows the pipeline's data (no automatic reduction). Planar captures use the output aspect ratio, one sample, no depth of field and at most 1024 pixels on the longest side. Other planar surfaces are excluded from captures to avoid recursion. Camera/quality changes reuse completed simulation textures; cancelling a partial bake discards it.
- Native material reflections are environment based; planar captures additionally include scene objects. Native transmission bends the view ray once at the entry surface and shades the opaque scene the camera sees through the exit point, as Three's screen-space transmission pass: it does not trace a second refraction or objects behind other transmissive layers, and `thickness` ignores the mesh scale. GI traces diffuse light bounces, but not specular paths, refracted paths or physical caustics.
- Shadow alpha uses a cutoff; transmissive materials cast full shadows, as in Three's shadow maps. Colored/translucent shadows and custom fragment-shader discard in shadow rays are not implemented. Ambient occlusion and soft shadows are evaluated once per pixel per triangle (MSAA shading), so their sample noise is not averaged by the antialiasing samples. Bloom and other whole-image effects are not implemented because buckets finish independently.
- Prefiltered environment levels (4 roughness steps, low resolution), rectangular lights, bump mapping and the Physical lobes (no multiple-scattering compensation) are approximations, not pixel-identical Three shading. Native transmission traces one camera ray per fragment instead of reading a mip-mapped transmission pass, so rough glass converges with the sample count; an exit point behind the camera falls back to the already rendered pixel.
- Anisotropic texture filtering, compressed/render-target textures, stencil operations and full depth-packing compatibility are not implemented.
- Animation is captured as a still scene; there is no CPU simulation clock advancing during a render. Skin/morph normals are recomputed and authored tangent frames are not preserved.

## Global illumination

Global illumination is enabled by `globalIllumination.enabled` in the settings and is off by default. Start with 64 GI samples and 3 diffuse bounces; use 16–32 samples for previews and 256–1024 for cleaner final images. These samples are independent of antialiasing: increasing AA does not reduce GI noise in the MSAA path. Depth of field evaluates GI at each lens sample.

The first visible surface is rasterized. GI traces cosine-weighted paths from it through the scene BVH, with one continuation per bounce. Native emissive triangles are additionally sampled by area × emission luminance; the power heuristic combines emission hits and explicit light samples without double counting ([PBRT path integration](https://pbr-book.org/4ed/Light_Transport_I_Surface_Reflection/A_Better_Path_Tracer)). Textures, vertex colors, normal maps, material sides, clipping and alpha coverage are evaluated at secondary hits. The bounce limit truncates longer paths; raising it recovers more indirect energy in interiors. Pixel seeds and sample dimensions are independent of bucket/worker order.

GI replaces the unoccluded diffuse environment and ambient/hemisphere fill, which are evaluated only when a ray escapes the scene. It does not add another ambient term or multiply traced light by ray AO. Environment rotation/intensity still apply, including with a transparent PNG background. Indirect visibility uses all surfaces independently of the artistic direct-shadow flags. Direct shading of the primary surface retains the existing shadow controls.

**Intensity** scales the complete indirect estimate once (1 preserves its energy). **Firefly clamp** limits each complete sample's linear luminance before averaging; 0 disables it. Clamping is deliberately off by default because it introduces bias. Small bright HDR sources may need many samples. Cost grows roughly with GI samples × bounces, and also with lens samples when DOF is enabled. Workers yield between pixels during expensive GI buckets so pause/revision changes remain cooperative.

Three optional accelerations sit on top of the integrator. The **irradiance cache** (`globalIllumination.cache` and `cacheSpacing`) is a whole-image phase before shading. The preparing worker allocates a grid of record cells (one per finest grid point, `irradianceCache.ts`, shared memory when available) and the client dispatches prepass jobs level by level (`prepassJobs`: 4, 2 and 1 grid steps, each job a band of grid rows across the full width). For each grid point the worker finds the visible surface with a camera ray through the BVH (same eligibility as rasterized shading: opaque, depth tested, color written, lit native material, correct side, alpha test), skips it when the existing records already cover it well (Ward's error with the window of `GRID_REACH` cells around the pixel; the summed weight must exceed `PLACEMENT_COVERAGE`, a single record at half its radius, so shading always blends several records), otherwise computes the full estimate and writes position, normal, color, variance and validity radius (harmonic mean distance of the first bounce times `CACHE_ACCURACY`, clamped between 1.5 and 3 grid steps of pixel footprint at that depth). Every record is previewed in gray through the progressive `pixels` channel, so the whole image dots in coarse to fine like Cinema 4D's prepass. Shading then interpolates the grid window around each fragment (records from neighbouring buckets included) with a weight that fades to zero at the edge of each record, `(1 − error)²`: Ward's `1/error` still weighs one where the record stops applying, which draws a step around every record. At lookup each record reaches `LOOKUP_SMOOTHING` times farther than at placement, so a point averages several times more records: each one carries its own sampling error, and interpolating few of them leaves low-frequency blotches that more samples barely reduce; fragments no record reaches compute their own estimate into a per-bucket list. Without shared memory each `cached` message carries the written cells and the client forwards them to every worker before shading. Without a client (captures, tests) `renderBucket` builds a per-bucket grid inline on its first pass. **Noise reduction** (`globalIllumination.denoise`) is an à-trous filter in the spirit of SVGF, guided by normal, view depth (with a per-pixel depth gradient) and the per-pixel variance of the GI estimate, which is filtered alongside. With the irradiance cache neighboring pixels share the error of the same records, and averaging them does not reduce it: the filter receives the reach of a record in pixels (`noiseCorrelation`) and only shrinks the variance once its step reaches that distance, otherwise the luminance threshold closes after the first passes and the records' noise survives as low-frequency blotches. It needs the whole image: the preparing worker allocates the AOV buffers (`denoise.ts`, shared memory when available; otherwise each bucket ships its packed slice and the client forwards them), every bucket writes color, modulation (diffuse albedo × coverage), indirect light, normal, depth and variance for its pixels, and after the last bucket the client asks the first worker to filter and recompose (`color + modulation × (filtered − indirect)`, then the same resolve as buckets), which arrives as `pixels` bands before `denoised`. Only opaque fragments of native lit materials contribute an indirect term; translucent fragments keep their GI in the unfiltered remainder. **Environment importance sampling** is automatic: when the base grid's brightest texel exceeds eight times the mean (a sun, small lamps), each bounce also samples one direction proportionally to luminance × sinθ and combines it with the cosine ray by the power heuristic. Paths also stop by Russian roulette from the second bounce on, with continuation probability tied to the hit material's albedo luminance.

This is diffuse GI, not parity with Cinema 4D/Redshift. Native glossy reflections retain their prefiltered environment approximation; transmissive surfaces conservatively block GI paths while reducing their diffuse contribution. Arbitrary custom fragment shaders have no recoverable BSDF/emission closure: they block GI and do not emit or receive it; native patched shaders retain their supported hooks with approximate camera-dependent inputs. Unlit Basic/Matcap/visualization materials block paths without becoming light sources. Point sprites have no world-space area and do not participate. Back faces of single-sided surfaces block rays without returning light. Deep alpha layering is bounded to 64 intersections and reports a diagnostic if exceeded.

## Performance notes

Measured single-threaded in Node on a 480 × 320 image with four samples: six Physical spheres with shadows went from 5.3 s to 0.35 s and a custom GLSL material from 11.1 s to 0.35 s. A later pass (same image, six Physical spheres with shadows, CPU time) took the native scene from 0.44 s to 0.31 s, a textured one from 0.55 s to 0.34 s and diffuse GI at 320 × 213 with 16 samples from 3.3 s to 1.8 s, with bit-identical output: material parameters are resolved once per material instead of looked up by name per fragment, light directions and spot cosines are cached per light, byte sRGB textures decode through Float32 lookup tables before filtering, the shading loop yields per row or every 8 ms instead of per pixel, the BVH is built with a binned SAH and traversed near-first with distance pruning, and GI rays that hit a material which can never let light through (`rayOpaque`) skip the coverage shade. What remains is spread thin (small array allocations in `surface`/`shade`, the coverage test evaluated twice per sample, component-wise vector ops in the GLSL compiler), so further gains need structural changes: scratch buffers for per-fragment vectors, typed slots inside the GLSL compiler, or shading several fragments of the same triangle together.

## Memory use

Ordinary image and unsigned-byte data textures keep RGBA8 pixels in the CPU snapshot instead of expanding to RGBA32F: a 4096 × 4096 texture uses **64 MiB instead of 256 MiB**. Resolution and source bytes are preserved. The sampler uses two tiny Float32 lookup tables for linear/sRGB values before nearest/bilinear filtering, preserving the previous Float32 results (including its rounding). HDR, compute outputs and planar captures retain linear Float32 storage. This reduces resident memory, unlike compressing a transport payload that must be fully expanded before sampling.

Image readback uses a 64-row scratch canvas and releases its backing surface in `finally`; textures are serialized sequentially with an event-loop yield between images. Texture clones sharing a Three source reuse pixel storage when their type/color space match, while retaining independent UV transforms/wrapping. Reused undeformed geometries and materials are copied once per snapshot, including their transfer-list entries. Skinned/morphed meshes remain separate. The geometry writer drops staging buffers before building world triangles and the BVH, and releases each JavaScript bucket bin after packing it.

Automatic concurrency is capped at eight because each worker still needs its own JavaScript runtime, materials and bucket scratch space even with shared typed arrays. Without cross-origin isolation/shared memory, a single worker avoids multiplying the entire prepared scene by the pool size; it also skips sending the frame, GI records and denoise AOVs back through the main thread. Manual concurrency remains available up to 32 when shared memory is available.

These changes reduce avoidable allocations, but do not guarantee a particular Safari memory limit. The host still owns its original geometry, decoded images and GPU resources, and preparation still needs transformed vertices and acceleration structures. Very large scenes can exceed the browser's available memory. `memory.test.ts` verifies storage size, exact sampling equivalence, deduplication and scratch-buffer release.

## Verification

From the repository root:

```sh
pnpm test        # unit and image tests (vitest, Node)
pnpm typecheck
pnpm bench       # single-threaded timings in Node, with an image signature per case
```

The bench reports preparation and shading time separately plus an FNV signature of the final image. A change that alters the signature changed the floating point results and must be reviewed as a visual change, not as an optimization. Read the header of `scripts/bench.ts` before trusting a number: use CPU time, warm the JIT with enough runs and repeat after thermal throttling.

## Procedural skies

A scene can replace the environment with a sky shader through `scene.userData.cpuRenderer.sky` (`ProceduralSky`): GLSL and uniforms instead of a GPU dome or cubemap. The preparing worker bakes a 128 × 64 linear atmosphere cooperatively, caches the completed result across camera/quality/geometry changes and shares it with the others. The optional foreground shader evaluates sun, moon and stars per background pixel; their discs are excluded from environment lighting to avoid counting a directional sun twice. The sky's `intensity` scales diffuse/GI/reflections, independently of its visible background. `background.mode` still selects transparent, solid color or environment, and the sky's `background` flag also applies. The environment rotation is ignored for a procedural sky so its world-space sun stays aligned with the directional light. Removing the sky restores the renderer's environment.

## Cross-origin isolation

Several workers share one prepared frame only when the page is cross-origin isolated, which requires serving it with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` (or `credentialless`) over HTTPS or localhost. Without isolation the renderer falls back to a single worker. Hosts that cannot set headers, such as GitHub Pages, can use a service worker like [coi-serviceworker](https://github.com/gzuidhof/coi-serviceworker), as the example does.
